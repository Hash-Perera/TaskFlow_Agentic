# TaskFlow API Contract

## 1. Purpose

This document defines the public REST API contract between the TaskFlow backend, frontend, automated tests, and AI development agents.

It is the source of truth for API behavior.

All agents working on API-related functionality must read this document before implementation.

Agents must not silently change this contract.

If an implementation requirement conflicts with this contract, the conflict must be reported for human review.

---

# 2. Base API

Development backend URL:

```text
http://localhost:3000
```

All TaskFlow task endpoints use the following base path:

```text
/api/tasks
```

Example:

```http
GET http://localhost:3000/api/tasks
```

The frontend must not hardcode this complete URL throughout multiple components.

The API base URL must be managed through centralized configuration.

---

# 3. Content Type

Requests containing JSON must use:

```http
Content-Type: application/json
```

Successful API responses containing data must use JSON.

---

# 4. Task Resource

The public Task resource has the following structure:

```json
{
  "id": "68abc1234567890123456789",
  "title": "Learn Codex orchestration",
  "description": "Practice parallel agent development",
  "status": "InProgress",
  "createdAt": "2026-08-24T02:30:00.000Z",
  "updatedAt": "2026-08-24T03:10:00.000Z"
}
```

## Fields

### id

Type:

```text
string
```

Description:

Public identifier for the task.

The backend uses MongoDB ObjectIds internally but exposes the identifier as:

```text
id
```

The public API must not expose MongoDB `_id` as the API identifier.

---

### title

Type:

```text
string
```

Required when creating a task.

Rules:

```text
minimum meaningful length: 1 character
maximum length: 150 characters
must not contain only whitespace
```

---

### description

Type:

```text
string
```

Optional.

Maximum length:

```text
1000 characters
```

---

### status

Allowed values:

```text
Pending
InProgress
Completed
```

Default value when creating a task:

```text
Pending
```

---

### createdAt

Type:

```text
ISO 8601 datetime string
```

Generated by the backend.

Example:

```text
2026-08-24T02:30:00.000Z
```

Clients must not provide this field when creating a task.

---

### updatedAt

Type:

```text
ISO 8601 datetime string
```

Generated and maintained by the backend.

Clients must not provide this field when creating or updating a task.

---

# 5. Create Task

## Endpoint

```http
POST /api/tasks
```

## Purpose

Create a new task.

---

## Request Body

```json
{
  "title": "Learn agentic development",
  "description": "Practice Codex workflows",
  "status": "Pending"
}
```

### Required fields

```text
title
```

### Optional fields

```text
description
status
```

If `status` is omitted:

```text
Pending
```

must be used.

---

## Successful Response

HTTP:

```text
201 Created
```

Body:

```json
{
  "id": "68abc1234567890123456789",
  "title": "Learn agentic development",
  "description": "Practice Codex workflows",
  "status": "Pending",
  "createdAt": "2026-08-24T02:30:00.000Z",
  "updatedAt": "2026-08-24T02:30:00.000Z"
}
```

---

## Validation Errors

The following must produce:

```text
400 Bad Request
```

Examples:

* missing title
* empty title
* whitespace-only title
* title longer than 150 characters
* description longer than 1000 characters
* unsupported status
* unsupported request properties

---

```json
    "status": "Pending",
    "createdAt": "2026-08-24T02:30:00.000Z",

  {
    "id": "68def1234567890123456789",

    "status": "InProgress",
    "createdAt": "2026-08-24T02:40:00.000Z",
    "updatedAt": "2026-08-24T03:00:00.000Z"
```

## Empty Collection

If no tasks exist:

HTTP:

```text
200 OK
```

```text
404 Not Found
```

# 8. Update Task

## Endpoint

```http
PATCH /api/tasks/:id
```

PATCH is used because TaskFlow supports partial updates.

Clients do not need to send the complete Task object.

---

## Supported Update Fields

The following fields may be updated:

```text
title
description
status
```

The following fields must not be client-controlled:

```text
id
createdAt
updatedAt
_id
```

---

## Example — Update Title

Request:

```http
PATCH /api/tasks/68abc1234567890123456789
```

Body:

```json
{
  "title": "Updated task title"
}
```

Successful response:

```text
200 OK
```

Body:

```json
{
  "id": "68abc1234567890123456789",
  "title": "Updated task title",
  "description": "Practice agentic development",
  "status": "Pending",
  "createdAt": "2026-08-24T02:30:00.000Z",
  "updatedAt": "2026-08-24T04:00:00.000Z"
}
```

---

## Example — Update Status

Request:

```json
{
  "status": "Completed"
}
```

Successful response:

```text
200 OK
```

The returned Task must contain:

```json
{
  "status": "Completed"
}
```

---

## Example — Update Multiple Fields

```json
{
  "title": "Complete Codex exercise",
  "description": "Finish orchestration practice",
  "status": "InProgress"
}
```

---

## Invalid Input

Invalid update data must return:

```text
400 Bad Request
```

Examples:

```json
{
  "title": ""
}
```

```json
{
  "title": "   "
}
```

```json
{
  "status": "Finished"
}
```

---

## Invalid ObjectId

```http
PATCH /api/tasks/not-a-valid-id
```

Response:

```text
400 Bad Request
```

---

## Task Not Found

If the supplied ObjectId is valid but no task exists:

```text
404 Not Found
```

---

# 9. Delete Task

## Endpoint

```http
DELETE /api/tasks/:id
```

Example:

```http
DELETE /api/tasks/68abc1234567890123456789
```

---

## Successful Response

```text
204 No Content
```

The response body must be empty.

After deletion:

```http
GET /api/tasks/:id
```

must return:

```text
404 Not Found
```

The deleted task must also no longer appear in:

```http
GET /api/tasks
```

---

## Invalid ObjectId

```http
DELETE /api/tasks/not-a-valid-id
```

Response:

```text
400 Bad Request
```

---

## Task Not Found

If the ID is valid but the task does not exist:

```text
404 Not Found
```

# 10. Error Response Contract

TaskFlow should use a consistent error structure.

NestJS may provide additional standard fields, but the API must expose at least useful HTTP status and message information.

Example validation response:

```json
{
  "statusCode": 400,
  "message": [
    "title should not be empty"
  ],
  "error": "Bad Request"
}
```

Example not-found response:

```json
{
  "statusCode": 404,
  "message": "Task not found",
  "error": "Not Found"
}
```

Clients must not receive:

* stack traces
* MongoDB connection strings
* credentials
* internal server paths
* raw database implementation details

---

# 11. Unknown Request Properties

The backend must reject unsupported input properties.

Example:

```json
{
  "title": "Test",
  "status": "Pending",
  "isAdmin": true
}
```

Expected:

```text
400 Bad Request
```

NestJS validation should therefore use behavior equivalent to:

```typescript
new ValidationPipe({
  whitelist: true,
  forbidNonWhitelisted: true,
  transform: true,
})
```

The exact implementation may vary, but the external behavior must match this contract.

---

# 12. Public ID Mapping

MongoDB documents internally use:

```text
_id
```

The public TaskFlow API uses:

```text
id
```

Example internal representation:

```json
{
  "_id": "68abc1234567890123456789"
}
```

Public representation:

```json
{
  "id": "68abc1234567890123456789"
}
```

The API must not require the React frontend to understand MongoDB-specific identifier behavior.

---

# 13. Task Status Contract

The only supported values are:

```text
Pending
InProgress
Completed
```

These values are case-sensitive.

Valid:

```json
{
  "status": "InProgress"
}
```

Invalid examples:

```text
inprogress
IN_PROGRESS
Started
Finished
Done
Complete
```

Agents must not introduce additional task statuses without updating this contract and receiving human approval.

---

# 14. Backend Environment Contract

The NestJS application must obtain the MongoDB connection from:

```text
MONGODB_URI
```

Example local development configuration:

```env
MONGODB_URI=mongodb://localhost:27017/taskflow
```

A safe example configuration may be committed as:

```text
.env.example
```

Real environment secrets must not be committed.

---

# 15. Frontend Environment Contract

The React application should obtain the backend URL from a Vite environment variable.

Recommended variable:

```text
VITE_API_BASE_URL
```

Example local configuration:

```env
VITE_API_BASE_URL=http://localhost:3000
```

The frontend API client may then construct:

```text
${VITE_API_BASE_URL}/api/tasks
```

The backend URL must not be duplicated across multiple React components.

---

# 16. Frontend Task Type

The frontend TypeScript representation should correspond to the public API.

Example:

```typescript
export type TaskStatus =
  | 'Pending'
  | 'InProgress'
  | 'Completed';

export interface Task {
  id: string;
  title: string;
  description?: string;
  status: TaskStatus;
  createdAt: string;
  updatedAt: string;
}
```

The frontend must use:

```text
id
```

not:

```text
_id
```

```typescript
export interface UpdateTaskInput {
```

# 19. API Summary

| Method | Endpoint         | Purpose            | Success |
| ------ | ---------------- | ------------------ | ------- |
| GET    | `/api/tasks`     | Retrieve all tasks | `200`   |
| GET    | `/api/tasks/:id` | Retrieve one task  | `200`   |
| POST   | `/api/tasks`     | Create task        | `201`   |
| PATCH  | `/api/tasks/:id` | Update task        | `200`   |
| DELETE | `/api/tasks/:id` | Delete task        | `204`   |

Common errors:

| Situation                      | Status |
| ------------------------------ | -----: |
| Invalid request                |  `400` |
| Invalid ObjectId               |  `400` |
| Task not found                 |  `404` |
| Unexpected application failure |  `500` |

# 20. Contract Ownership

This document is jointly consumed by:

```text
Backend Agent
Frontend Agent
Testing Agent
Reviewer Agent
Human Engineer
```

No implementation agent owns the API contract.

Contract changes require explicit human approval.

For example, Backend Agent must not decide:

```text
PATCH is inconvenient.
I will change it to PUT.
```

Frontend Agent must not decide:

```text
I prefer "Done" instead of "Completed".
```

Testing Agent must not change expectations merely because production code behaves differently.

The agreed contract remains the source of truth.

---

# 21. Agent Conflict Rule

If an agent discovers that implementing its assigned task would require changing this contract, it must:

1. Stop changing the affected contract behavior.
2. Report the conflict.
3. Explain why the change appears necessary.
4. Suggest a contract modification if appropriate.
5. Wait for human approval before changing the contract.

This prevents one parallel agent from silently breaking the work of other agents.

---

# 22. Definition of API Compatibility

An implementation is API-compatible when:

* endpoint paths match this document
* HTTP methods match
* request structures match
* response structures match
* status values match
* validation behavior matches
* expected HTTP status codes match
* public identifiers use `id`
* unsupported properties are rejected

Passing compilation alone does not prove API compatibility.

Automated tests and human review must verify the contract.
